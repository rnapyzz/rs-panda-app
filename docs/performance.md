# 速さの計測（I-15）

本番に近い量のデータで、主な画面・操作の API の時間を測った結果と、測り方をまとめる。本番の前、データ量が大きく増えたとき、集計の仕組みを変えたときに測り直す。

## 測り方

```bash
make perf
```

- `scripts/perf.sh` が、開発環境の MySQL に専用の DB（`perf_fpanda`）を作り、`perfseed`（`api/src/bin/perfseed.rs`）で下のデータを入れ、API（最適化したビルド）を別のポート（18090）で起動して測る。終わったら DB を消す（`KEEP=1` で残す、`SEED=0` で既存の DB で測るだけにする）。
- 開発用の DB（`fpanda`）は使わない。`perfseed` は DB 名が `perf_` で始まり、施策が1件もない DB にしか入れない。
- 各 API を3回呼んだ中央値。手元の Docker（MySQL 8.4、Mac）での値なので、本番（RDS）では絶対値が変わる。前後の比較と、桁の目安に使う。

## データ量

| データ | 行数 | 内容 |
| --- | ---: | --- |
| 施策 | 2,000 | ユニット 40、担当者 160、内訳とマイルストーン（2件）付き |
| シナリオ | 31 | 3年度分の月次の見込（今回の見込は 2026年10月見込、ほかはロック済み） |
| 金額（`budget_facts`） | 1,488,000 | 版 × 施策 × 12か月 × 2行 |
| 実績の合計（`actual_facts`） | 120,030 | 30か月分 |
| 保存した実績（`scenario_actuals`） | 588,147 | ロック済みの版の、決算確定月までの実績 |
| 実績の明細（`actual_entries`） | 200,000 | 2026年4〜9月 |
| 監査ログ（`audit_logs`） | 501,000 | うち期日の後ろ倒し 1,000 |

## 結果（ミリ秒）

API を Rust に入れ替えたとき（2026-10）に、同じデータ・同じマシンで、入れ替え前の Go 版と Rust 版を交互に7回呼んだ中央値。「マイルストーン」「未割当の一覧」と、実績の取込は `make perf` の値。

| 画面・操作 | API | Go 版 | Rust 版 |
| --- | --- | ---: | ---: |
| ホーム（FP&A・全施策） | `GET /api/scenarios/{id}/activity-status?scope=all` | 178 | 176 |
| ホームのマイルストーン（200施策） | `GET /api/scenarios/{id}/milestones` | 4 | 6 |
| 数値入力（1施策） | `GET /api/scenarios/{id}/activities/{aid}` | 3 | 5 |
| 施策の一覧 | `GET /api/activities` | 7 | 8 |
| 予実比較（2版＋実績） | `GET /api/reports/comparison` | 168 | 172 |
| 予実比較（加重見込） | `GET /api/reports/comparison?measure=weighted` | 192 | 197 |
| リスク画面・施策の一覧の図（比較あり） | `GET /api/reports/risk` | 431 | 370 |
| リスク画面（比較なし） | `GET /api/reports/risk` | 326 | 288 |
| 変更履歴（全体） | `GET /api/change-sets` | 440 | 483 |
| 変更履歴（1施策） | `GET /api/change-sets?activity_id=` | 438 | 484 |
| 実績の修正の食い違い（FP&A のホーム・シナリオ管理） | `GET /api/scenarios/actual-drift` | 634 | 636 |
| 未割当の一覧 | `GET /api/actuals/unallocated` | — | 3 |
| 計画値の CSV（金額） | `GET /api/scenarios/{id}/amounts/export` | 73 | 101 |
| 実績の取込の確認（20万行） | `POST /api/actuals/import?dry_run=true` | 7,534 | 5,630 |

どれも目安（下）の中に収まっている。時間の大半は DB の集計で、Go 版と Rust 版の差は小さい。同じデータでのレスポンスは、リスク画面・予実比較（加重見込）・ホームで Go 版と一致することを確かめた。

## 対応したこと

- **実績の修正の食い違い**（3.7秒 → 0.8秒）: ロック済みの全シナリオについて、保存した実績と今の実績を施策 × 科目で突き合わせていた（約120万行の集計）。今の実績はシナリオによらないので、まず（シナリオ, 月）ごとの要約（行数・合計・行の内容のチェックサム）を比べ、違う（シナリオ, 月）だけを詳しく比べるようにした（`api/src/actual/drift.rs`）。食い違いがなければ、詳しい比較は行わない。
- **実績の取込**（10.2秒 → 7.5秒）: 合計（`actual_facts`）の更新と監査ログを1件ずつ書いていた（約8,000回の SQL）。まとめて書くようにした（`audit::Recorder::many`）。明細の INSERT は 1回 2,000 行にした。残りの多くは 20万行の明細を書く時間で、上限の行数での値なので、月1回の取込では許容する。
- **ホーム・リスク画面**（約1秒 → 0.5秒）: シナリオごとの集計（今回・目標・期初計画・修正計画・前回の見込、比較・複製元の版）を順番に読んでいた。互いに関係しないので並行して読むようにした。Rust 版も、互いに関係しない読み込みを別々のコネクションで並行して行う。

- **Rust に入れ替えたときに直したこと**:
  - 実績の取込（97秒 → 5.6秒）: CSV の行番号を、行ごとにファイルの先頭から数えていた（行数の2乗の時間）。前の行の位置から数え足すようにした（`api/src/csvio.rs`）。
  - リスク画面（0.77秒 → 0.37秒）: 楽観・加重見込・悲観の合計を、行ごとに有理数で足していた（1回ごとに約分する）。標準の確率は小数4桁なので、1円の 1/10,000 を単位にした整数で足すようにした。誤差はなく、結果は変わらない（`api/src/report/risk.rs`）。

## 残っている重いところ（今は対応しない）

| 処理 | 状況 | 重くなったときの手 |
| --- | --- | --- |
| 実績の修正の食い違い（0.8秒） | 保存した実績（約59万行）の要約を毎回集計している | ロックしたときに（シナリオ, 月）ごとの要約を保存し、毎回の集計をやめる |
| 金額の集計（版ごと 0.1〜0.3秒） | `scenario_amounts` ビュー（計画値と実績の UNION）を版ごとに集計している | 金額（`amount`）を含む索引、または版 × 施策の年間の合計の保持 |
| 変更履歴の一覧（0.5秒） | 変更セットごとの監査ログの件数と、施策での絞り込み（監査ログの JSON の検索）。計測のデータは監査ログ 50万行が1つの変更セットに入っているため、実際より重い | 監査ログに施策 ID の列（生成列）と索引を足す |
| 実績の取込（7.5秒） | 20万行の明細を書く時間が大半 | 確認（dry run）では明細を書かずに集計する |

目安として、毎日使う画面（ホーム・施策・数値入力・リスク・予実比較）は 1秒未満、月1回の操作（取込）は 10秒未満を保つ。
